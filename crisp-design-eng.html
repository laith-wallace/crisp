CRISP Design Engineering

The craft intelligence layer of the CRISP framework. Closes the gap between an interface that works and an interface that feels right. Every decision maps to a CRISP dimension.

Core principle

The CRISP framework scores five dimensions. Design engineering asks a sixth question the framework does not score:

Does it feel the way it should?

This is not a soft question. An interface fails to feel right when:

Feedback is delayed relative to the user's action. Elements appear or disappear without physical logic. Motion runs at the wrong frequency for how often users trigger it. Easing creates a perception of slowness the system does not deserve. Invisible details are wrong enough, in aggregate, to erode trust without the user being able to say why.

These are engineering problems. They have engineering solutions. This document names and fixes them.

The details users never consciously notice are the ones that matter most. A thousand invisible details, each correct, produce something that feels right without the user being able to say why.

Color strategy framework

Color decisions made after implementation has started are corrective, not intentional. Make the strategy decision first.

Step 1: Pick a commitment level

LevelWhat it meansWhen to use
RestrainedOne accent on 10% of screen or lessProduct UIs, data-dense dashboards
CommittedAccent on 30-60% of screenConsumer apps, surfaces needing warmth
Full palette3-4 colour rolesBrand surfaces, marketing pages
DrenchedThe surface IS the colourHero moments, onboarding splash

Step 2: Write the scene sentence

One sentence of physical context. It must force the dark-vs-light decision by itself.

Weak
"An analytics dashboard."
Strong
"A finance analyst reviewing end-of-quarter risk on a 27-inch monitor at 6am."

Step 3: Color rules

OKLCH for all new colour values. oklch(0.65 0.18 142) not #4caf50. OKLCH is perceptually uniform. sRGB hex is forbidden for new tokens.

Never pure black or pure white. Always tint neutrals. Dark backgrounds: oklch(10% 0.01 240). Light backgrounds: oklch(98% 0.005 90).

High chroma only at lightness extremes. Saturated colours at middle lightness (40-60% L) are hard to use accessibly.

Font selection doctrine

Typography shapes emotional register before a single word is read. Most AI-assisted design reaches for the same training-data defaults.

Reflex-reject list

Do not select these without a specific, documented reason:

Fraunces, Newsreader, Lora, Crimson Pro, Playfair Display, Cormorant Garamond, Syne, IBM Plex Sans, IBM Plex Mono, Space Mono, Space Grotesk, Inter, DM Sans, DM Serif Display, Outfit, Plus Jakarta Sans, Instrument Sans, Instrument Serif

These are not bad fonts. They are fonts so frequently reached for by AI systems that selecting them produces a legible design signal: AI made this.

Font selection procedure (Brand register)

1. Write three voice words as physical objects, not adjectives. "Worn leather, index card, CRT glow" not "modern, friendly, professional."

2. List fonts you would naturally reach for. Reject any on the reflex-reject list.

3. Find a font by its physical object: the typeface on a 1970s technical manual, a museum caption card, a pharmaceutical insert.

4. Reject the first pick that "looks designy." That instinct is the training-data default.

5. Cross-check: elegant does not equal serif. Technical does not equal sans. The automatic association is the trap.

Product register

CSS
/* Product register body */ font-family: -apple-system, BlinkMacSystemFont, 'Segoe UI', sans-serif;

Motion decision framework

Before writing any animation code, answer these questions in sequence.

Question 1: Should this animate at all?

Trigger frequencyDecision
100+/day (shortcuts, nav toggle)No animation. Remove it.
Tens/day (hover, tabs)Reduce or remove
Occasional (modals, drawers, toasts)Standard animation
Rare (onboarding, celebrations)Can carry more weight
Never animate keyboard-initiated actions. These fire hundreds of times daily. Animation here fails R . It makes the interface feel slower than it is.

Question 2: What is this animation for?

Every motion must pass at least one test: clarifies cause and effect, or adds deliberate delight on a low-frequency surface. If it passes neither, remove it.

PurposeExample
Spatial orientationToast enters and exits from same direction
State confirmationButton scales on press
State transitionMorphing feedback icon
Preventing jarring discontinuityElement appearing without transition feels broken
ExplanatoryFirst-run animation showing how a feature works

Question 3: What easing?

ContextEasing
Entering or exitingease-out
Moving between two statesease-in-out
Hover state or colour changeease
Constant/looping motionlinear
Defaultease-out
Never use ease-in on UI elements. Ease-in starts slowly. The moment the user takes action is the moment they watch most closely. A dropdown at 300ms ease-in feels slower than the same dropdown at 300ms ease-out.
CSS
/* CRISP motion tokens */ --ease-out: cubic-bezier(0.16, 1, 0.3, 1); --ease-in-out: cubic-bezier(0.45, 0, 0.55, 1); --ease-drawer: cubic-bezier(0.32, 0.72, 0, 1);

Question 4: How long?

ElementDuration
Button press feedback100-160ms
Tooltips, small popovers125-200ms
Dropdowns, selects150-250ms
Modals, drawers200-500ms
Marketing / explanatoryMay be longer

UI animations: stay under 300ms. A 180ms dropdown feels more responsive than a 400ms one. Perceived performance is real performance from the user's point of view. R

Component craft rules

These are not suggestions. Each has a CRISP dimension it protects.

Buttons must confirm they were pressed R

Add transform: scale(0.97) on :active. No exceptions for interactive elements.

CSS
.btn-primary, .btn-ghost { transition: transform var(--duration-fast) var(--ease-out), opacity var(--duration-fast) var(--ease-out); } .btn-primary:active, .btn-ghost:active { transform: scale(0.97); }

Nothing enters from scale(0) R

Nothing in the physical world appears from nothing. Start from scale(0.95) combined with opacity: 0.

Fails R
.entering { transform: scale(0); }
Correct
.entering { transform: scale(0.95); opacity: 0; }

Popovers scale from their trigger C

A popover expanding from centre looks like a modal. It breaks spatial orientation.

CSS
.popover-content { transform-origin: var(--radix-popover-content-transform-origin); }

Never use transition: all R

Always list only the properties you intend to animate. transition: all accidentally animates layout-affecting properties causing reflows and jank.

Fails
.btn { transition: all 200ms; }
Correct
.btn { transition: transform 150ms ease-out, opacity 150ms ease-out; }

Animations must be interruptible R

Every animation must be cancellable by user input. CSS transitions handle interruption correctly. They retarget mid-animation. Keyframe animations restart from zero and should not block input.

Stagger list entries S

Everything appearing at once reads as a page refresh. Keep stagger increments short: 30-80ms per item. Never block interaction while stagger animations run.

Asymmetric enter/exit timing R

Enter can be measured. Exit must be fast. When a user dismisses something, the system responds to clear intent. Delay here is friction.

CSS
.drawer { transition: transform 300ms var(--ease-drawer); } .drawer.is-closing { transition: transform 150ms var(--ease-out); }

Clip-path as animation tool

clip-path animates on the GPU and enables patterns that opacity and transform cannot produce.

The inset shape

CSS
.hidden { clip-path: inset(0 100% 0 0); } .visible { clip-path: inset(0 0 0 0); }

Hold-to-confirm pattern P

Use clip-path: inset(0 100% 0 0) on a coloured overlay. On :active, transition to inset(0) over 2s with linear timing. On release, snap back at 200ms ease-out. The hold duration signals intentional action. The fast release signals responsiveness.

CSS
.btn-danger .overlay { clip-path: inset(0 100% 0 0); transition: clip-path 200ms var(--ease-out); background: rgba(255, 60, 60, 0.15); border-radius: inherit; } .btn-danger:active .overlay { clip-path: inset(0); transition: clip-path 2s linear; }

Scroll reveals

Trigger .is-visible with IntersectionObserver at rootMargin: '-80px'. Use once: true. The reveal should not replay on scroll-back.

Spring physics

Springs simulate real physics. They settle rather than stop. They maintain velocity when interrupted. Use for gesture-driven interactions. Do not use for standard UI state transitions.

JS
// Readable (Apple's approach) { type: 'spring', duration: 0.4, bounce: 0.15 } // More control { type: 'spring', stiffness: 300, damping: 30 }

Keep bounce below 0.25 for product UI. Reserve higher values for onboarding or explicitly playful contexts.

Gesture and drag craft

Dismiss on velocity, not distance S

JS
const velocity = Math.abs(dragDistance) / elapsedMs; if (Math.abs(dragDistance) > THRESHOLD || velocity > 0.11) { dismiss(); }

Damping at boundaries

When a user drags past the natural boundary, apply damping. The more they drag, the less the element moves. Hard stops feel broken.

Pointer capture

Once dragging starts, capture all pointer events. Drag continues even if the pointer leaves the element bounds.

Multi-touch protection

Ignore additional touch points after the initial drag begins. Without this, switching fingers mid-drag causes the element to jump.

Performance rules

Animate transform and opacity only

transform and opacity bypass layout and paint and run on the GPU. Animating padding, height, width, or margin triggers the full rendering pipeline. R

Do not update CSS variables in gesture handlers

CSS variables on a parent recalculate styles for all children. Updating --drag-offset on a container during pointermove recalculates every child on every frame.

Recalculates all children
element.style.setProperty( '--drag-offset', `${distance}px` );
Only affects this element
element.style.transform = `translateY(${distance}px)`;

Framer Motion shorthand is not GPU-accelerated

Main thread
<motion.div animate={{ x: 100 }} />
GPU-accelerated
<motion.div animate={{ transform: 'translateX(100px)' }} />

Debugging craft violations

Test at reduced speed. Before shipping, test animations at 5x duration. Issues invisible at full speed become obvious in slow motion: incorrect easing, wrong transform-origin, properties going out of sync.

Test on real devices. For gesture interactions, test on physical hardware. Simulator gesture behaviour is not representative. Connect via USB, visit local dev server by IP, use remote devtools.

Review the next day. Timing issues invisible during development become obvious with distance. What felt "slightly slow" reads as "clearly slow" the next morning.

Accessibility

prefers-reduced-motion

Reduced motion means fewer and gentler animations, not zero. Preserve opacity and colour transitions that aid comprehension. Remove all transform-based motion. S

CSS
@media (prefers-reduced-motion: reduce) { .animated-element { transition: opacity var(--duration-fast) var(--ease-out); } }

Touch device hover guard

CSS
@media (hover: hover) and (pointer: fine) { .element:hover { background: var(--surface-2); } }

Touch devices fire :hover on tap. Without this guard, hover animations misfire on every tap.

CRISP token reference

CSS
--ease-out: cubic-bezier(0.16, 1, 0.3, 1); --ease-in-out: cubic-bezier(0.45, 0, 0.55, 1); --duration-fast: 150ms; --duration-base: 300ms; --duration-slow: 500ms; --duration-thread: 800ms; /* Lineage timeline only */

--duration-thread is the one case where 800ms is correct. The lineage timeline draw is structural, not interactive. Every other UI interaction observes the 300ms ceiling.

No decorative motion. If removing the animation does not change what the user understands, remove it.
